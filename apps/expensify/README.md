# Expensify

Create expenses, reports and policies, read policies and domain cards, export and download report
data, run card reconciliation, and update policies, tag approvers, expense rules and employees,
over the **Expensify Integration Server**.

- **Categories** — finance, hr
- **Auth methods** — partner-credentials (`partnerUserID` + `partnerUserSecret`)
- **Actions** — 15
- **Health checks** — `service` (status.expensify.com, `Integration APIs` component), `api` (unsigned
  reachability), `quota` (declared absence, informational) + the derived `auth:partner-credentials`
- **Egress allowlist** — `integrations.expensify.com`
- **API docs** — https://integrations.expensify.com/Integration-Server/doc/
- **Icon** — the Simple Icons Expensify mark, https://cdn.jsdelivr.net/npm/simple-icons@latest/icons/expensify.svg,
  embedded verbatim

Everything here was verified on 2026-10-06 against the Integration Server reference (and its
`/doc/employeeUpdater/` page) and live probes of the endpoint.

## How credentials are applied (they are only ever in `sign`)

Expensify has no auth header. The credential pair is a `credentials` object **inside** the JSON held
in the `requestJobDescription` form field, so there is nothing for the runtime to stamp on a header.
The split of work:

1. An action builds the job (`{type, inputSettings, …}`) with **no `credentials` key** and posts it
   form-encoded with `ctx.fetch` (`lib/client.ts`, `buildBody`).
2. The connection's `sign` hook (`auth/partner.ts`, `signBody`) — the only code handed the secret —
   parses the form body, sets `requestJobDescription.credentials = {partnerUserID,
   partnerUserSecret}` and re-serialises. Other form fields (`template`, `data`) and all other job
   keys pass through untouched.
3. `credentials` is **overwritten, never merged**, so a job can't smuggle its own `authToken`,
   `feedUrl` or `sftp` block next to the stored pair. `sign` throws if the body has no
   `requestJobDescription`, rather than letting an unsigned job go out.

`Auth.test` runs a signed `get`/`policyList` (it returns policy names, never the credential).

## Things most likely to go wrong

1. **HTTP status is never the verdict.** A wrong credential pair, a missing `requestJobDescription`
   and an unknown job type are all `HTTP 200` with `{"responseMessage": "...", "responseCode": 404 |
   500 | 403}` (measured). Every action and the credential test read the body's `responseCode`; a
   client that checks `res.ok` will treat a failed job as success.
2. **Error codes are in-band and inconsistent.** Bad credentials are `404 "Authentication error"`;
   no credentials is `403`; validation is `410`; "generic" is `500`, which also covers unrelated
   failures. The report-status updater alone can answer `207` (partial) — that action returns the
   `skippedReports`/`failedReports` lists instead of throwing.
3. **Exports are two steps.** `export-reports` and `run-reconciliation` only generate a file and
   return its name; `download-file` fetches it (`fileSystem: reconciliation` for reconciliation
   output). A failed download is the JSON error envelope at HTTP 200, not an error status.
4. **Domain-restricted features.** `create-report` needs concierge@expensify.com to enable it
   ("Not authorized to authenticate as user" until then); `create-expenses` with `employeeEmail`,
   `list-domain-cards` and `run-reconciliation` need credentials generated by a domain admin; acting
   as another user (`userEmail`/`employeeEmail`) needs third-party access granted by that user.
5. **Field names differ between jobs.** Expense dates are `created` in Create Expenses but `date` in
   Create Report; amounts are integer cents everywhere (including category `maxExpenseAmount`);
   dates must be `yyyy-mm-dd` or the job fails with 410. Actions check this before the request.
6. **Rate limits are small and not observable:** 5 requests / 10 s and 20 / 60 s, 429 past them, no
   headroom header — hence the `quota` check is a declared absence.
7. **Credentials are shown once** at the Integrations page of your Expensify account (Settings → Tools → Integrations); a lost secret
   means generating a new pair.

## Actions

| Area             | Actions                                                                                          |
| ---------------- | ------------------------------------------------------------------------------------------------ |
| Create           | `create-expenses`, `create-report`, `create-policy`, `create-expense-rule`                        |
| Read             | `list-policies`, `get-policy`, `list-domain-cards`                                                |
| Export, download | `export-reports`, `run-reconciliation`, `download-file`                                           |
| Update           | `update-policy`, `update-report-status`, `update-tag-approvers`, `update-expense-rule`, `update-employees` |

`update-employees` uses the **Advanced Employee Updater** (`dataSource: "request"`, `entity:
"generic"`) and defaults to a dry run.

## Left out

- **The CSV "Employee updater"** (`inputSettings.type: "employees"` with `fileType: "csv"`): marked
  "no longer maintained" in the reference, which points to the Advanced Employee Updater instead.
- **OAuth2 partner auth** (`credentials.authToken`): documented as private beta and requires a
  client id/secret registered with Expensify; only partner credentials are offered.
- **Advanced Employee Updater `download` and `sftp` data sources**: they put a feed URL/password or
  SFTP login inside `credentials`, which only `sign` may write. The `request` source covers the job.
- **Export `sftpUpload` finish action** (SFTP password in the job) and the **CSV/TSV tag-file mode**
  of the policy updater (the reference lists `fileType` as `"cvs" or "tsv"` in one place and
  `csv` in its example, so the format is not pinned down). Inline JSON tags are supported
  (independent tag levels only).
- **Unconfirmed against a live account:** the success body of `returnRandomFileName`. The reference
  says only that it "returns the name of the generated report", so `export-reports` accepts a bare
  name or a JSON envelope with `filename`.

## Health

- **Credential** — derived from `Auth.test` (`get`/`policyList`). Classified from the body:
  `responseCode 200` with a `policyList` array passes; `404`/"Authentication error" is a rejected
  pair; `429` is reported as rate limiting; a body without the envelope is reported as such.
- **service** — `status.expensify.com` (Statuspage v2; page id `n6mt6bg37zmv`). Of its 20
  components, `Integration APIs` decides; `Report PDFs` is capped at degraded; the rest (mobile app,
  bank feeds, SMS, Chat…) are detail. A wrong page, missing component, 5xx or bad JSON is `unknown`.
- **api** — unsigned policyList job; the `{responseCode, responseMessage}` envelope with 403/404 is a
  pass (it proves the Integration Server answered).
- **quota** — declared absence (`informational`): limits are documented but no header or endpoint
  exposes headroom.
