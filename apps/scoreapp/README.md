# ScoreApp

List scorecards (quiz funnels), read their questions and scoring categories, and read the results
(leads) they collect with each result's per-question answers, on **ScoreApp's Open API**
(`open-api.scoreapp.com`).

- **Categories** — forms, marketing, crm
- **Auth methods** — bearer API key (`Authorization: Bearer <key>`; no OAuth surface exists)
- **Actions** — 6, all read-only (4 `read`, 2 `search`; the API documents no write at all)
- **Health checks** — `service` (declared absence, `informational`) + `rate-limit` (a real quota
  probe) + the derived `auth:api-key`
- **Egress allowlist** — `open-api.scoreapp.com` and nothing else (there is no status host to add)
- **Website** — https://www.scoreapp.com
- **API docs** — https://support.scoreapp.com/article/217-scoreapp-public-api-getting-started
- **Status page** — none published (checked live; see below)

> **Everything below was verified against ScoreApp's own sources on 2026-09-22** — the vendor's
> single reference article, "ScoreApp Public API - Getting Started" (last updated 2026-08-03, and
> the *complete* reference: every endpoint, parameter, response shape and status code ScoreApp
> documents lives on that one page), plus live probes against `open-api.scoreapp.com` and the
> status hosts. Nothing here came from a third-party integration directory, and no endpoint was
> inferred from a sibling app.

## The four things most likely to go wrong

### 1. The API host is not the obvious guess

`api.scoreapp.com` and `developer.scoreapp.com` both answer **`302` to `www.scoreapp.com`** — the
marketing site, not an API. The real origin is `open-api.scoreapp.com`, and it answers all six
documented paths with `401 {"error":"Unauthenticated."}` unauthenticated — never a `404`, never a
generic HTML shell (verified live, all six paths). [`lib/client.ts`](lib/client.ts) is the only
place the origin is written down.

### 2. Without `Accept: application/json`, every auth failure looks like a redirect problem

ScoreApp is a Laravel application, and Laravel's default answer to an unauthenticated request that
does not ask for JSON is a **`302` to `/login` with an HTML body**. With the header, the same
request answers `401 {"error":"Unauthenticated."}`. So the header is sent on every request this app
makes, and `lib/client.ts` additionally **refuses to hand back a non-JSON body** rather than letting
a login page be parsed as a result set — `res.ok` is `true` for a followed redirect that landed on
HTML, so the status alone cannot catch it. The auth probe reports a `3xx` as *that trap*, not as a
bad key.

### 3. The vendor's own docs disagree about the id shape

The `List Scorecards` response example shows **UUID** ids
(`"9e01daab-49c6-428b-9209-b5b0607acad3"`), while the `questions`, `categories`, `results` and
`answers` endpoints document the very same `{scorecard}`/`{result}` path parameters as
**`(integer, required)`** and use small integers in their example URLs (`/scorecards/1/results`).
This app resolves that by never deciding: every path id is a `string` param, passed through
verbatim (trimmed and path-escaped, never `Number()`-ed, with no numeric validation), which is the
safe reading whichever shape an account actually has.

### 4. Rate-limit headroom is real and readable here — and the docs disagree with the wire

Unlike most vendors in this pack, ScoreApp sends `x-ratelimit-limit` **and**
`x-ratelimit-remaining` on **every** response, including its `401`s, and the remaining count
genuinely decrements per request (measured live: six consecutive calls returned `119 → 114`). The
docs say "100 requests per minute"; the live header says `120`. Nothing in this app hardcodes
either number — [`health/rate-limit.ts`](health/rate-limit.ts) reads the headers and reports what
the wire says. No reset header was observed, so no `resetAt` is reported.

## Auth

**A bearer API key.** Generated by the account holder in ScoreApp's own UI — *ScoreApp logo >
Account settings > API keys > add API key* — and sent as `Authorization: Bearer <key>`. The article
documents no second auth mode and no OAuth surface, so this app ships one method. The full key is
shown **once**, at creation, and cannot be retrieved later; the connection form says so, because a
half-saved key has to be regenerated rather than looked up.

### The probe is `GET /scorecards?limit=1`

All six documented paths require a credential, so the choice is about cost and shape:

- it is the shortest path, and `?limit=1` asks for one scorecard instead of the default hundred;
- the same call is what the `rate-limit` health check reads its headers off, so the two checks cost
  one request a minute between them;
- no ScoreApp response shape contains the API key or any other secret — there is no "current user"
  endpoint in this API at all — so no probe here can echo a credential.

Classification is from the **body**, never the status alone: `401` with
`{"error":"Unauthenticated."}` is reported as a rejected key; a `401` *without* that body is
reported as an unexpected refusal rather than telling someone to regenerate a working key; and a
`422` is reported as a query-parameter validation error in this app, never conflated with an auth
failure.

There is **no `afterConnect`**: the article documents no account-identity endpoint — no `/me`, no
account object — and this app does not invent one to get a nicer connection label. (A
`connectionLabel` template with no variables to fill would render as literal braces, so it is
omitted too.)

## Actions

Every action returns the vendor's own response envelope **verbatim** — `{"data": …}`, plus
`links`/`meta` on the two paginated reads — because `meta.total` and `links.next` are how a
workflow walks a collection. Nothing is unwrapped or renamed.

| Action | Method + path | Notes |
|---|---|---|
| `scorecard-list` | `GET /scorecards` | Paginated. Filter by `status` (draft/live/template) and free-text `search` |
| `scorecard-questions-get` | `GET /scorecards/{scorecard}/questions` | Not paginated. Each question carries its options and scoring categories |
| `scorecard-categories-get` | `GET /scorecards/{scorecard}/categories` | Not paginated. Returns visible **and** hidden categories |
| `result-list` | `GET /scorecards/{scorecard}/results` | Paginated leads. Date window, status, response count, search, ordering; `limit` capped at 100 |
| `result-get` | `GET /scorecards/{scorecard}/results/{result}` | One lead, with optional `include[]` |
| `result-answers-get` | `GET /scorecards/{scorecard}/results/{result}/answers` | One lead's per-question answers |

### `include[]` is a repeated parameter

`result-get` accepts `include[]` with the five documented values — `answers`, `scores`, `source`,
`activity`, `additional_data` — and sends it the way the vendor's own examples spell it:
`?include[]=answers&include[]=scores`. The key repeats once per value; a comma-joined value is a
*different* request and is never sent. `additional_data` is documented as **Pro-plan-only and
requiring an email address on the result**, and asking for it otherwise is documented as a `403` —
`lib/client.ts` says so in the error instead of reporting a bare status.

`result-answers-get` reads the same answers as `result-get?include[]=answers`, but it is the cheaper
of the two: the single-result read returns the result row, its scores, UTM source and activity log
alongside the answers, while this endpoint returns the answers and nothing else.

### Read-only, by the vendor's design

ScoreApp documents no create, update or delete of scorecards or results through this API, so every
action here is a list or a get and none declares `idempotent`. If you find yourself wanting a
"create scorecard" action, the answer is ScoreApp's own UI — or a webhook, which is out of scope
below.

### Not covered, deliberately

- **Webhooks** — ScoreApp's webhook feature (`support.scoreapp.com/article/101-webhooks`) is
  configured in ScoreApp's own UI and pushes out; it is not part of this REST surface, and this app
  declares no triggers.
- **ScoreApp's ~15 third-party integrations** (HubSpot, Zapier, Mailchimp, …) — those are
  ScoreApp-side connections to other vendors, not endpoints of this API.
- **Anything not in the one reference article.** No undocumented endpoint was added on a guess.

## Health checks

### `service` — a declared absence, at `informational` severity

ScoreApp publishes no status page. Checked live on 2026-09-22:

| Host | Answer |
|---|---|
| `status.scoreapp.com` | `302` → `https://www.scoreapp.com/` (the marketing site) |
| `scoreapp.statuspage.io` | `302` → `https://www.statuspage.io` (the unclaimed-Statuspage decoy) |

No Instatus or Better Stack alias for "ScoreApp" was found either. This is stated as a positive
fact, not left as a gap. `severity: "informational"` is load-bearing: an `unavailable` entry always
reports `unknown`, and `unknown` outranks `ok` in a roll-up, so any other severity would pin this
app's verdict at `unknown` forever. The derived `auth:api-key` check is the automatable signal for
"is ScoreApp working" for anyone holding a live key.

### `rate-limit` — a real quota probe, not an absence

`x-ratelimit-limit` / `x-ratelimit-remaining` read off the same signed `GET /scorecards?limit=1`
call the credential probe makes. Both headers are present on every response, so this app gets a
genuine headroom number where most of this pack has to declare one unavailable. Exhaustion is
reported as `degraded`, **never** `down` — a per-minute window refills on its own and the documented
remedy is to wait — and a response the API *refused* reports `unknown` rather than printing headers
that describe the IP's window instead of this connection's. No `resetAt` is reported: no reset
header was observed on the wire.

## Not independently verified against a live 200

This app has **no ScoreApp account**, so the *success* response shapes are the vendor's own
documented examples, not a live authenticated probe:

- Everything about the **request** side is verified live — the host, all six paths (`401` + the
  documented JSON error, never a `404`), the `Accept: application/json` behaviour, the rate-limit
  headers and their decrement, and the dead status/`api` hosts.
- Everything about the **response body** — field names such as `id`, `key`, `domain`, `status`,
  `purchased`, `answer_type`, `scoring_logic`, and the `data`/`links`/`meta` pagination envelope —
  is taken verbatim from the vendor's examples in that one article.
- Consequently, the field-level assertions in `tests/` pin this app's own mapping, not a live
  payload. If a documented field is ever renamed on the wire, nothing here will notice until
  someone runs it against a real account; that is the limit of what could be checked without one.

The one place the docs and the wire were **measured to disagree** is the rate limit (100/minute
documented, `120` on the wire). The wire wins, and neither number is hardcoded.

## Icon

`assets/icon.png` is ScoreApp's own mark, downloaded verbatim from
`https://cdn.scoreapp.com/site/uploads/2026/07/cropped-ScoreApp_Icon_Logo_Navy-270x270.png` —
the image ScoreApp's own `www.scoreapp.com` `<head>` links as its `apple-touch-icon`, confirmed
live as `image/png`, 270×270, 13,564 bytes. No SVG exists anywhere: `favicon.svg`,
`apple-touch-icon.png` and `apple-touch-icon-precomposed.png` all `404` on `www.scoreapp.com`,
simple-icons has no `scoreapp` entry, and n8n's `nodes-base` ships no ScoreApp node — so the vendor's
PNG is used rather than a fabricated SVG, the same pattern as `apps/amplitude` and `apps/braze`.

docker compose -f .devcontainer/docker-compose.yml exec -T api sh -c \
  'cd /app/.worktrees/apps-batch/scoreapp/apps/scoreapp && deno task validate && deno task check && deno task lint && deno task test'
